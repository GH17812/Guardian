注意事项：

- 若"远程画面正常"为否：记录现象（黑屏/花屏/分辨率异常/卡顿）并勾选界面验证失败；同时记录自动恢复是否正常。

### 1.1 本机实测结论（Sunshine + Moonlight，2026-11-14）

- 本机显示器 **不支持 DDC/CI**（`DDC/CI available: False`），显示隐私走 SC_MONITORPOWER 广播回退路径。
- SC_MONITORPOWER 关屏会复位 GPU 显示输出，与 Sunshine 帧捕获冲突，实测现象：
  1. 串流端光标卡顿/瞬移（周期重申压黑导致画面管线反复复位）；
  2. 屏幕已关闭时启动串流 → 会话无法建立；
  3. 串流中开启保护后，退出串流再重连 → 无法建立会话。
- 已实施的兼容策略（0.1.0 后续构建）：
  - 检测到 Sunshine TCP 端口段（47989-48010）存在 ESTABLISHED 连接即判定"串流中"，
    期间**暂停关屏并恢复显示**（显示隐私降级，主界面"显示隐私"磁贴如实显示"暂缓"）；
  - 串流结束后经 10 秒宽限期再恢复压黑，避免快速重连被打断；
  - 非串流期间关屏重申间隔 3 秒（原 1 秒过频，加剧 GPU 抖动）。
- 结论：本机"串流期间物理关屏"与"串流流畅"不可兼得（硬件限制），当前默认**可用性优先**。
  若需串流期间本机屏幕熄灭，需硬件支持 DDC/CI（显示器 VCP 0xD6）或虚拟显示器方案（Phase 2 评估）。

### 1.2 串流结束后的窗口位置异常（虚拟显示器方案，2026-11-15）

- 环境：虚拟显示器（Virtual Display Driver / MTT1337）扩展在主屏右侧（逻辑 3200,0；物理 3200,0，800x600）；
  Sunshine `dd_configuration_option=ensure_only_display`，串流结束后物理屏恢复为主屏。
- 现象：串流结束后，串流期间位于虚拟显示器上的程序窗口保留旧坐标，落在物理屏之外，
  任务栏有图标但桌面看不到窗口；重启该程序仍不恢复（坐标由应用自身保存）。
- 根因：显示拓扑切换只改变坐标空间，不会把已有窗口搬回；窗口位置属于各进程自己的状态，外部程序无法通过重启修复。
- 处理：新增 `OffscreenWindowRescue`（客户端交互会话执行），在显示拓扑变化（`SystemEvents.DisplaySettingsChanged`）
  与程序启动后延时执行救援：把落在物理显示器上可见面积不足一半、或尺寸超出工作区的非最大化顶层窗口，
  移回主显示器工作区居中显示；串流进行中不做处理；无法枚举到物理显示器时不做任何处理（fail-open）。
- 注意：窗口坐标必须在 `DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2` 上下文中读写，否则高 DPI 缩放会导致尺寸翻倍。

### 1.3 串流期间“黑屏但界面显示未启动”（2026-11-15）

- 现象：串流开始后物理屏自动熄灭（Sunshine `ensure_only_display` 停用物理屏，与 Guardian 无关）；
  此时打开 Guardian，界面显示“已关闭”，用户误以为保护状态显示错误。
- 日志证据：客户端进程在串流启动时停止心跳（`00:14:45` 连接并上报设备，`00:15:09` 即首次心跳超时），
  服务端按 fail-open 策略自动恢复；由于恢复逻辑**每个 5s tick 重复触发**，日志被“客户端心跳超时”刷屏。
  且心跳此前挂在 WPF `DispatcherTimer`（UI 线程）上，UI 线程一旦卡顿/进程异常，心跳即中断，
  服务端 15 秒后误判“客户端丢失”并静默解除保护。
- 根因与修复（0.1.0 后续构建）：
  1. 客户端心跳迁移到后台线程（`System.Threading.Timer` 语义），与 UI 线程解耦，
     只有进程真正退出才触发服务端 fail-open；UI 更新经 Dispatcher 调度并合并防积压。
  2. 服务端“客户端丢失”恢复同一丢失事件只执行一次（`_clientLostHandled`），心跳恢复后重新武装；
     且仅在确有保护资源（手动保护/会话/策略生效）时执行，无保护时不再刷日志。
  3. 快照新增 `LastRecoveryReason`，界面“最近操作”人话化：
     “保护已自动解除：客户端失联（应用被关闭或异常退出）”，如实说明保护为何消失。
  4. 界面新增串流提示：检测到串流会话且保护未开启时显示
     “本机屏幕熄灭由串流端（虚拟显示器）接管，并非 Guardian 保护生效”，消除“黑屏=保护中”的误解。
- 实测验证：客户端关闭 25 秒（无保护状态），服务端日志零新增（此前每 5s 刷屏）；
  单次恢复/重新武装/无保护不恢复三条新测试与全量 61 测试通过。
- 结论：黑屏 ≠ 保护生效。串流期间屏幕熄灭是 Sunshine 虚拟显示器行为；Guardian 界面现在会如实标注来源。

### 1.4 先开启保护再串流：启动卡顿与退出后屏幕不恢复（2026-11-15）

- 现象：开启隐私保护后启动串流，串流端卡顿、光标瞬移；退出串流后物理屏不亮，
  取消保护后屏幕仍不恢复，反复串流多次才点亮。
- 根因 1（卡顿）：检测到串流的瞬间，客户端曾广播 `MONITOR_ON` 开屏，而 Sunshine 随即
  （毫秒级）停用物理屏，形成“开屏→再被拔掉”的电源切换，GPU 输出复位导致帧捕获抖动与光标重映射。
- 根因 2（黑屏不恢复）：取消保护只广播一次 `MONITOR_ON`；若落在 Sunshine 拓扑恢复窗口内则失效，
  且无任何重试；仅当“先取消保护（面板电源状态置为开）再退出串流（Sunshine 恢复物理屏）”的
  顺序才可点亮——与用户实测的恢复顺序一致。
- 修复（0.1.0 后续构建）：
  1. 进入串流暂缓时**不再广播开屏**，仅停止关屏重申（物理屏本就被 Sunshine 停用，无需电源切换）；
  2. 取消保护后的恢复改为“立即 + 2s/6s/15s/30s 重试 + `mouse_event` 净位移微动兜底”
     （微动唤醒 DPMS 为本机已验证手段）；保护重新开启时旧重试自动作废（代际计数）。
  3. 显示隐私执行器新增 `Diagnostics` 事件，全部状态迁移写入 `app-debug.log`（`[display]` 前缀），
     便于下次复现时定位。
- 说明：退出串流后物理屏变黑是**设计行为**——保护仍生效，宽限期后恢复压黑；
  需要屏幕亮起时应取消保护（本次修复保证取消后一定点亮）。

### 1.5 串流检测失检：UDP 视频导致 “Slow connection”（2026-11-15）

- 现象：开保护后串流端仍卡顿，Moonlight 提示 `Slow connection to PC, Reduce your bitrate`；
  不开保护则正常。
- 日志证据（`[display]` 诊断）：整个串流期间无任何 `streaming detected: suppressed` 记录，
  关屏重申（3s 一次）持续击中被捕获的显示器；串流启动时 `streaming note` 出现 2 秒后消失。
- 根因：Moonlight 视频走 **UDP**（47998-48010），TCP 控制连接仅在会话建立时短暂存在，
  原有“Sunshine TCP 端口检测”在串流中途失检 → 关屏重申误击串流捕获链路 → 帧产出变慢。
- 修复（0.1.0 后续构建）：串流检测升级为双信号（任一命中即串流中）：
  1. 原有 Sunshine TCP 端口检测（保留，覆盖会话建立阶段）；
  2. **物理显示器拓扑信号**：`ensure_only_display` 串流期间物理屏从活动显示器拓扑中消失，
     该信号贯穿整个会话（新增 `DisplayTopology`，与窗口救援共享显示器枚举逻辑）。
- 验证：无串流时检测返回 false（本机探针实测）；串流期间的持续性由用户复测确认
  （预期日志出现 `streaming detected: suppressed` 且不再有串流期 `MONITOR_OFF` 重申）。
- 追加（同日）：日志证实检测修复生效后（串流期间零 `MONITOR_OFF`），残留卡顿来自
  **串流中途取消保护时的唤醒广播**——`MONITOR_ON` + 鼠标微动打在 Sunshine 正在捕获的显示器上。
  修复：串流期间取消保护改为“推迟唤醒”（`_wakePending`），等串流结束、物理屏恢复后再点亮；
  唤醒重试等待期间若串流再次开始，同样转为推迟；`TryTurnOnLocked` 增加串流守卫，
  确保串流期间 Guardian 完全静默（零电源广播）。

### 1.6 紧急热键“一闪恢复→又黑屏→闪回”（2026-11-15）

- 现象：保护开启时按紧急快捷键，屏幕瞬间恢复后又黑屏并闪回（有/无串流两种场景均出现）。
- 日志证据：`hotkey PRESSED` 后本地立即恢复（`privacy off`），约 1 秒内又出现
  `privacy active`（旧快照，服务端恢复尚未完成）→ 屏幕被重新关掉；恢复快照到达后再点亮，
  形成“亮→黑→亮”闪回。服务端日志确认恢复本身正常（`reason=EmergencyHotkey → 恢复完成`）。
- 根因：心跳（1s）送回的服务端旧快照与服务端恢复命令存在竞态——本地 fail-open 先恢复了显示，
  旧快照又把保护标志带回来重新关屏。
- 修复：紧急热键触发后开启 3 秒**本地快照覆盖**（`_emergencyLocalOverride`），
  覆盖期间忽略旧快照的显示/输入保护标志（本地保持恢复状态），3 秒后自动失效；
  顺带在紧急路径本地立即释放输入隔离钩子（此前要等服务端快照返回才解除）。
- 说明：紧急快捷键的语义是“无条件解除全部保护”（fail-open），按完后界面显示“已关闭”
  是**正确行为**，需要保护时重新开启即可。

### 1.7 虚拟显示器会话后物理屏无法被唤醒（2026-11-15）

- 现象：开保护 → 串流 → 退出串流后，物理屏“变亮→闪回几次→变黑”（Sunshine 恢复 +
  宽限期压黑的正常过程），此时按紧急键，`MONITOR_ON` 广播 + 鼠标微动 + 4 次重试全部无效，
  屏幕始终黑着；唯一恢复办法是再开一次串流再退出（Sunshine 重新挂载物理屏时面板点亮）。
- 日志证据：唤醒路径完整执行（`privacy off: wake display` + 重试 1~4 全部 `MONITOR_ON`），
  屏幕不亮；随后用户开启新串流（`streaming detected`）并退出（`stream ended: deferred wake`）后恢复。
- 根因：虚拟显示器会话结束后，面板对 DPMS 唤醒消息无响应（挂载事件是唯一可靠唤醒手段）。
  另发现本机 `SetDisplayConfig`（CCD）对任何输入返回 `ERROR_INVALID_PARAMETER`（原因不明），
  而 `ChangeDisplaySettingsEx`（Sunshine 同族旧版 API）全部成功——已实测。
- 修复（0.1.0 后续构建）：
  1. 新增 `DisplayReattacher`：用 `ChangeDisplaySettingsEx` 把物理显示器“摘下→等待 700ms→插回
     （原模式）”，强制面板输出管线重新初始化；插回失败走 `displayswitch /extend` 兜底并重试；
  2. 串流结束后的 2 分钟窗口内，唤醒重试第 1 次（+2s）附带重挂载兜底；串流中绝不执行；
  3. 唤醒升级为三级：`MONITOR_ON` 广播 → `ES_DISPLAY_REQUIRED` 脉冲 → 30px 往返鼠标微动
     （1px 微动可能被输入合并忽略）。
- 验证：探针实测摘除/插回四步全部 `DISP_CHANGE_SUCCESSFUL`；集成后 `ReattachPhysicalDisplays=True`；
  61 测试全绿。

## 6. 待机模式（PS5 式，2026-11-16 新增能力）

- 需求：电脑睡眠后串流不可达；要求"PS5 式待机"——睡眠转为待机、串流随时可连、
  退出待机需要凭证（密码）。
- 本机环境：支持 S3 睡眠 + 休眠，无 Modern Standby（`powercfg /a` 实测）。
- 方案（基于 Windows 离开模式 Away Mode，与 PS5 待机语义一致）：
  1. 服务端持有 `ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_AWAYMODE_REQUIRED` 电源请求
     （PowerRequestController 扩展），睡眠动作（合盖/电源键/菜单/定时）转为离开模式：
     屏幕熄灭、系统保持运行、网络在线——Sunshine 持续可达；
  2. 客户端"待机会话"：开关开启立即熄灭屏幕（复用显示执行器的双熄灭源架构：
     隐私保护 + 待机会话，任一生效保持熄灭）；本地物理键鼠输入（INJECTED 过滤）唤醒；

     Guardian 不接触任何凭据；

     覆盖"合盖→离开模式→开盖输入"路径的凭证要求。
- 优先级规则：保护 > 待机（保护生效期间本地输入不唤醒）；串流 > 待机（串流期间绝不唤醒/锁屏）；
  输入隔离下本地输入被拦，唯一本地逃生通道是紧急快捷键（全面恢复 + 退出待机 + 锁屏）。
- 安全与限制：
  - 待机期间系统实际不睡眠（功耗高于 S3）：屏幕熄灭 + 音频由离开模式静音；

  - 不拦截休眠（S4）——建议用户把电源计划"休眠"设为从不；

    服务重启后自动恢复（RestModeArmed 持久化）。

- 追加（同日，开启待机即锁屏 + 桌面巨卡，日志实证）：
  1. **现象**：点开待机开关 → 屏幕熄灭 → 约 0.5 秒后屏幕又亮并进入锁屏；

- 追加（同日，紧急键优先级 + 屏亮复黑，日志实证）：
  1. **现象**：开保护 → 按紧急键 → 屏亮一下 → 迅速复黑；只能开串流再退出才恢复。

     - 虚拟屏摘除方案废弃（实测 ChangeDisplaySettingsEx 对 VDD/IndirectKmd 无效，
       rc=0 但显示器仍在拓扑），改用 `CursorBoundaryClip`：ClipCursor 把光标钳制在
       物理屏并集内，串流中自动释放（远程光标需要虚拟屏），拓扑变化与 1 秒轮询保底。
- 追加（同日，紧急键彻底失效回归，日志实证）：
  1. **现象**：开保护 → 按紧急键 → 屏闪回 2 次后变黑；串流端显示保护仍开（服务端

     记录——RegisterHotKey 通道全程未触发（窗口隐藏后 HWND 消息泵或热键竞争失效），
     闪回是“键盘输入点亮 DPMS 面板 → 3 秒重申压黑”的循环。
  2. **根因**：紧急键此前有两条通道：RegisterHotKey（依赖主窗口消息泵，窗口隐藏/
     UI 线程卡顿/热键竞争任一发生即失效）与待机钩子自备识别（仅待机武装时运行）。
     仅开保护（未武装待机）时只有第一条通道可用，失效即“紧急键完全无反应”。
  3. **修复**：
     - 输入钩子生命周期扩展：待机武装**或**保护生效（显示隐私/输入隔离任一）时运行；
       保护期间吞掉会点亮 DPMS 屏的物理输入（防闪屏——此前该行为只覆盖待机场景）；
     - 紧急组合键由钩子自备识别（GetAsyncKeyState 校验修饰键 + 2 秒防抖），
       **不依赖 RegisterHotKey 与 UI 消息泵**——紧急通道永远在线；
     - RegisterHotKey 保留为冗余第二通道（双触发幂等无害）。

## 7. 串流环境一键启用 / 一键卸载（2026-11-19 新增能力）

### 7.1 分发路线：国内直连可行性（实测）

| 目标 | 结果 |
| --- | --- |
| `github.com` / `api.github.com` / `cdn.winget.microsoft.com` | 可达（VPN 关闭、ProxyEnable=0） |
| release 资源实际下载 | 206，经 `release-assets.githubusercontent.com`（Fastly），**约 214 KB/s**，33 MB 的 Sunshine MSI 约 3 分钟 |
| `raw.githubusercontent.com` | **不通（code=000）** |

结论：
1. 一键安装走"Guardian 自己 HTTPS 下载 + 钉死 SHA256"可行，但**必须可中断、有进度、失败有明确原因**——3 分钟不是瞬间动作；
2. 任何实现**不得读取 GitHub 仓库文本文件**（raw 域名不可达），需要的取值一律从本机已安装的产物或 API 取证；
3. `winget` 是 per-user 打包应用，Session 0 的 SYSTEM 服务里不采用。
4. 完整性已端到端验证：Sunshine MSI 33,710,080 B 本地 SHA256 == winget 清单值 `1d7fed8b…7e0ccf`，Authenticode 有效（CN=David Lane）；`MttVDD.dll` Authenticode 有效（SignPath Foundation）；VDD driver-only 包 132,118 B（SHA256 `e2421069…`，官方未公布该包哈希，故以我们观测值 + 目录内文件签名双重把关）。选 driver-only 包把下载量从 100 MB 级降到约 32 MB。

### 7.2 output_name（虚拟屏显示标识）只能探测，不能推算

- 本机取证：GUID `{9acddf6d-…}` **不落注册表**（`HKLM\SYSTEM\CurrentControlSet\Control\GraphicsDrivers\Configuration` 子项数为 0），`sunshine_state.json` 中也不存在；
- **唯一可靠来源**是 Sunshine 日志里的 `Currently available display devices:` JSON 块，条目含 `device_id`（即 output_name）、`display_name`、`edid.manufacturer_id`、`friendly_name`、`info.primary`，可据此分辨虚拟屏与物理面板；
- `display_device.state` 有同一 GUID 但**没有厂商字段**，无法单独分辨哪台是虚拟屏，只能作旁证；
- 按 UUIDv5 尝试复算：4 个 namespace × 21 个候选名称 × 5 种编码 = 840 组，**全部不匹配**（算法本身已用本机 Python 3.11 `uuid.uuid5(NAMESPACE_DNS,'python.org') = 886313e1-3b8a-5372-9b90-0c9aee199e5d` 校验通过；注意 DNS namespace 是 `6ba7b810-…`，`6ba7b812-…` 是 OID）。
- 因此实现取"解析 Sunshine 自身输出"为事实来源；命中 0 条或多条时**一律拒写** `ensure_only_display`（写错标识会停用物理屏却没有任何可用输出）。

### 7.3 枚举互锁为何要求"两侧同时命中"（2026-11-19 晚些时候已改为分级互锁，见 7.9）

"设备存在且已启用"不等于"有屏幕可用"。实测：Sunshine 是在**客户端连上的瞬间**才把拓扑切成只留虚拟屏（日志 `Newly computed display device topology data: - topology: [["{VDD-guid}"]]`）。若虚拟屏没有真正产出输出，写入 `ensure_only_display` 后本地既看不见也点不动。因此一键启用要求：

1. Sunshine 自己的设备清单里能判定出虚拟屏（服务端 Session 0 可得）；**且**
2. 交互会话在 30 秒新鲜期内上报枚举到虚拟屏（客户端上报，见 7.4）。

任一不成立即 `Blocked`，界面原样显示拦停原因，不得改写成"成功"。

### 7.4 Session 0 的边界（再次确认）

服务端（Session 0）**枚举不到显示器**，因此"虚拟屏是否成为可用输出""物理屏是否已被停用"只能由交互会话上报，协议新增 `report-streaming-topology`（只带计数与布尔，不带分辨率、设备名，更不带屏幕内容）。同理，"夺回物理主显"（`DisplayReattacher`）只能在客户端执行：管道是请求/应答模型、服务端无推送通道，故用档案上的 `PhysicalRestorePending` 标志 + 客户端轮询领取，等不到回执就如实报"未确认"。

### 7.5 命令行输出不可解析（重要教训）

`pnputil` / MSI 的中文输出是 OEM 代码页，.NET 里读回是乱码（实测 `sc.exe qdescription` 同现）。**把乱码当依据会把成功读成失败**。实现纪律：只取退出码，结论一律用动作之后重新探测的实测状态（SetupAPI 设备状态、注册表/文件、Sunshine 日志）表述。

### 7.6 本次一并修掉的三个状态缺陷

1. **应用启动即黑屏（用户报告）**：`RestModeController.SetArmed(true)` 会直接 `EnterSession()` 熄屏，而主界面用**启动后的第一个快照**同步服务端持久化的 `RestModeActive` —— 恢复上次设置被当成了"用户要求立即待机"。实测日志：`17:59:52.126 [rest] armed` → `.127 [rest] session entered (display off)`。修复后为 `[rest] armed (restored, session kept off)` 且无熄屏行；用户主动勾选仍按原设计立即进入待机。
2. **`_wakePending` 缺推迟起点**：唤醒重试链中发现串流又开始时只置 `_wakePending=true` 而未设 `_wakeDeferredAt`，导致 20 秒强制点亮兜底（`expired` 判定依赖该时间戳）**永不触发**；串流检测一旦误判，屏幕再无机会点亮，违背 fail-open。改为 `_wakeDeferredAt ??= DateTime.UtcNow`（保留已有起点，不反复续期）。
3. **`_restStreamingActive` 在武装时未复位/未取用**：未武装期间 `SetStreamingActive` 被 `!_restModeActive` 闸门直接吞掉，于是"正在串流时开启待机"会以 `_restStreamingActive=false` 计算并**打开离开模式**——离开模式静音音频端点，实测导致 Sunshine 音频流建立失败。改为始终记住最近一次上报值（`_streamingReported`），`EnableRestMode` 用它兜底；客户端武装后 1 秒内重报真值自动纠偏。回归测试：`RestMode_ArmedWhileStreaming_DoesNotOpenAwayMode`。

### 7.7 一键卸载不删驱动

`一键恢复` = 还原 Sunshine 配置（按首次接管前的原始值，逐键还原，**不做整文件回滚**——Web UI 保存会重写整个文件，覆盖备份会抹掉用户之后改的设置）→ 重启服务 → 夺回物理主显 → **禁用**虚拟设备。驱动包保留在驱动存储中，下次一键启用秒级恢复；这也避开了卸载驱动带来的重启需求。

### 7.9 结构性卡点：虚拟屏"有路径"不等于"在桌面里"（2026-11-19 21:13 实测）

用户点完一轮"一键恢复 + 一键启用"后实测：恢复四步全部成功（含之前失败的禁用设备），但**启用被互锁拦住且无法重试成功**。取证如下：

| 观测面 | 结果 |
| --- | --- |
| PnP `ROOT\DISPLAY\0000` | Status=OK，CM_PROB_NONE（设备已启用、驱动已启动） |
| `EnumDisplayDevices` | `\\.\DISPLAY6`（Virtual Display Driver）flags=0x1 ACTIVE；`\\.\DISPLAY6\Monitor0` flags=0x3 ACTIVE\|ATTACHED |
| 客户端 `EnumDisplayMonitors` | 只有物理面板，**虚拟屏不在桌面布局里** |
| Sunshine 自己的设备清单（最后一次启动） | 只有 1 台：`{9e2806e4-…}` AUO 物理屏 |
| 生效配置 | `output_name` / `dd_configuration_option` 三个键都不存在（还原后删掉了） |

结论与推论纠正：我之前判断"设备启用后虚拟输出自然存在"是错的。**"有显示路径"与"是能当屏幕用的输出"是两件事**，而把路径拉进桌面的正是 Sunshine 的 `dd_config`；可 `dd_config` 又需要 `output_name`，而 `output_name` 只能从"已进桌面的清单"里读到。原互锁（要求客户端枚举命中才允许写任何配置）因此**结构性启不来**，而不是偶发失败。

改造（用户批准的三条）：

1. 互锁分级。`VirtualDisplayEnvironmentInfo.PathActive`（EnumDisplayDevices 级别的 ACTIVE|ATTACHED 路径）是**第一阶段**的前提；`Enumerated`（真进桌面）是**第二阶段**（停用物理屏）的前提。没有路径时两个阶段都不写；有路径未进桌面时只允许写不停物理屏的那一档。
2. `output_name` 取值加第三级来源：Guardian 把当场确认过的标识持久化在设置里（`VirtualOutputGuid` + 时刻），界面取证必须写明"上次记在设置里的值，不是本次当场命中"。另加自举：取不到时先重启虚拟设备（禁用→启用，不碰物理屏）让驱动重建监视器对象，再让 Sunshine 重新枚举一次；仍取不到就拒绝写入。
3. 接管拆成两阶段两状态：`SunshineActivating`（写 `ensure_primary` + 重启）→ 复验进桌面 → `SunshineTakeover`（写 `ensure_only_display` + 重启）。新增环境状态 `Activating`（"已激活，物理屏仍亮，未完成接管"），它既不是 Ready 也不算失败——停在半程时本机始终有一块能用的屏幕。

端到端已跑通（21:49:48 第三次点击，同一版本 + 等待窗口修正前）：`SunshineActivating=Ok → SunshineTakeover=Ok → SunshineRunning=Ok`，21:49:54 状态 Ready；配置文件、Sunshine 日志生效值、Sunshine 设备清单（`{9acddf6d-…}` = `\\.\DISPLAY8`）、客户端上报四方一致，用户实测 Moonlight 串流正常。中间 21:49:50 短暂 PartialFailure 是"文件已写、服务尚未重启完"的真实漂移，3 秒后自洽。

由此修正上面那句"结构性启不来"：**根因是驱动造屏为分钟级**，不是造不出来。21:42:35 那次 15 秒等待后判无路径，而同一适配器在 21:49 已带监视器对象出现并一路成功。因此等待窗口按 45 秒给，拦停文案改为可操作的两步（过一两分钟再点一次；始终无路径才用 VDD Control 添加显示）。逆向厂商接口的方案据此撤销——主线不需要。

实测补充（21:41 - 21:42 第二轮点击）：一键恢复四步全绿（含禁用虚拟设备），随后一键启用被第一道互锁拦住，理由写作"没有可用显示路径"——但那是**读得太快**：设备启用后 devnode 标志约 100ms 就翻转，而显示路径挂上来、客户端 3 秒一轮的上报刷新都要更久。现在第一道互锁也走有界等待（25 次 × 600ms，拦停理由里带"已等待约 N 秒"），并在 Sunshine 重启后轮等设备清单落地（30 秒上限）而不是立刻读——21:36 那次误判就是这么来的。同轮还纠回一条被我写松的规则：`Enumerated` 只信交互会话的新鲜上报，不能用"Sunshine 日志里有这块屏"替代（两个红测拦下了这次放宽）。

配套：日志去重改为按"状态 + 每步结论签名"判定，避免"启用被拦停但状态没变"时整次操作不留记录（21:13:23 那次就被吞过）；新增回归测试 `Enable_NoDisplayPath_InterlocksBeforeAnyConfigWrite`、`Enable_PathActiveButNeverEntersDesktop_StopsAtActivatePhase`，以及 `SetupDiSetClassInstallParams` 结构校验（见 7.10）。测试：Contracts 5 / Core 60 / Integration 52。

### 7.14 全新机深度取证：我们侧四个真 bug + 一个上游硬限制（2026-11-21）

用户在新机（Win11 26200、RTX 4060 Laptop、独显直连、iGPU 未被枚举、ToDesk `Root	dIdd` 共存）提交了一份取证包，逐条核实后如下。

**我们侧的 bug（全部已修，测试 5 / 62 / 53）**

1. `SetupDiSetDeviceRegistryProperty` 我按 4 个参数声明，官方 `SetupAPI.h`（10.0.26100）是 **5 个**（少 `PropertyBufferSize`）。后果不是报错而是**静默写空**：硬件 ID 为空 → 驱动无法绑定 → 每点一次一键启用就多一个孤儿根设备（新机出现过 `ROOT\DISPLAY 0`、`0002` 两个）。现在补齐参数，并在登记后**把硬件 ID 读回来核对**，不匹配就明确失败 —— 这类"API 返回 TRUE 但内容是空的"错误只能靠回读自证。
2. `DIF_REGISTERDEVICE` 之后只等 PnP 自己绑驱动，实测出现过 `Service` 为空。现在显式调用 `UpdateDriverForPlugAndPlayDevices`（`newdev.h`：`INSTALLFLAG_FORCE|INSTALLFLAG_NONINTERACTIVE`），并把绑定结果与"是否需重启"写进取证。
3. **完全没有放置驱动的建屏设置**。MttVDD 只在设备启动时读 `C:\VirtualDisplayDriverdd_settings.xml`，缺文件就一个监视器都不创建（厂商工具那句 `No sample XML file found to create default settings` 同源）。现在一键启用会从钉死包里**只在缺失时**写入该文件，绝不覆盖已有配置。
4. `install.ps1` 没注册开机自启，`App.xaml.cs` 也不解析 `--minimized`。后果是安全性的：重启后若没人打开客户端，**紧急热键与显示隐私执行体都不在场**，而服务端仍报"健康"。现在安装器写 `HKLM\...\Run` 以 `--minimized` 自启，卸载器同步清除。

**上游硬限制（不是我们能用顺序或等待解决的）**

新机的驱动调试日志显示：驱动读到设置、`Creating Monitor: 1`、35 条目标模式交付、`Monitor arrival successfully reported`，随后 **`Failed to set device to swap chain. HRESULT: -2005270490`（`0x887A0026` = `DXGI_ERROR_ACCESS_LOST`）**，接着 `Unassigning swap chain` 把监视器拆掉 —— 于是 `EnumDisplayDevices` 层面始终没有显示路径。提交者给出的解释是：OS 在 assign 回调里给的 `RenderAdapterLuid: 79619-0` 与驱动自己建 D3D 设备用的 `LUID: 254616002-0`（Vendor 0x10DE / Device 0x28E0）不是同一个适配器。**这套 LUID 推断来自他们的日志与分析，我尚未独立复现，只作为高可信度线索记录。** 他们也已排除两种常见误判（WARP 回退：Feature Level 0xB100=11_1 是硬件；目标模式未交付：日志有两次 pass）。

同时他们实测：`<gpu><friendlyname>` 改成 NVIDIA / ToDesk / Microsoft Basic 三种值并重启设备，`ASSIGNED GPU` 行与失败结果**每次都一样** —— 说明该版本里配置项并不能改变实际使用的适配器。

**产品结论**

- 在**独显直连（dGPU-only）笔记本**上，当前公开发布的签名 VDD（`11.30.4.434`，DriverVer 2024-12-24，随 25.7.23 发布）造不出可用虚拟输出；Guardian 的一键启用会正确地停在互锁上，物理屏不受影响 —— 这是设计行为，不是失败。
- 因此不能把"一键启用"宣传为在所有硬件上可用；用户说明需写明该限制，界面在拦停时应指向驱动日志 `C:\VirtualDisplayDriver\Logs\log_*.txt` 里的 `Failed to set device to swap chain` 这一句（读取该日志需要先取得同意，尚未实现）。
- 上游那份报告还指出：最新 tag 25.7.23 里的显示驱动比同 release 的其它资产旧得多，`master` 上的修复从未随签名驱动发布 —— 也就是说等官方修好并签名发布之前，我们这边无论怎么改顺序都拿不到屏幕。
### 7.13 全新机第三轮：ToDesk 撞名与两处 P/Invoke 错误（2026-11-21）

新机诊断数据（用户提供）：`ROOT\DISPLAY 1` 的 FriendlyName 是 **Todesk Virtual Display Adapter**、`DriverVersion 16.44.2.509`、`Service=WUDFRd`，状态 OK；WUDFHost 进程存在。也就是说那台机器上**根本没有 MttVDD** —— Guardian 把 ToDesk 的根设备认成了自己的，判定"根设备已存在"，于是跳过装驱动与建设备，后续每一步都"成功"却永远造不出虚拟屏。厂商工具此时报 `The driver may be installed but is not running`、`Pipe exists but cannot communicate`，完全吻合。

顺藤摸出两处我自己的实现错误：

1. **实例 ID 前缀兜底匹配**：为"硬件 ID 万一读不到"加的 `ROOT\DISPLAY\` 前缀兜底，把第三方驱动认成了本方设备。已删除 —— 读不到硬件 ID 就报未找到，绝不猜。
2. **SetupAPI 绑到了 A 版接口**：`SetupDiGetDeviceRegistryProperty` 等未指定 EntryPoint 时绑定 ANSI 版本，返回的 REG_MULTI_SZ 是 ANSI 字节，按 UTF-16 解码得到 `潒瑯䵜瑴䑖D` 这类乱码；同时 `SetupDiSetDeviceRegistryProperty` 我传的是 UTF-16 字节，写入硬件 ID 也会错。已全部显式绑 `...W`。
3. **"问长度"的那一次调用被当成失败**：Win32 约定第一次 `PropertyBuffer=NULL` 调用必然返回 FALSE 并填所需字节数，我写成 `if (!ok || needed==0) return 空` —— 于是硬件 ID 永远读不到，正是这条让第 1 条兜底成为唯一的"能工作"路径，把错误掩盖到全新机器上才暴露。

修正后判定链：设备认领只看硬件 ID `Root\MttVDD`；客户端拓扑只认自己驱动的适配器（`DeviceID` 含 MttVDD 或描述为 VDD/MTT/Virtual Display Driver）；Sunshine 日志的虚拟屏线索去掉泛用词 `virtual`/`idd`/`indirect`，只留 `vdd`/`mtt`/`virtual display driver`。回归测试：`FindVirtual_IgnoresThirdPartyVirtualAdapters`（ToDesk 条目不得被认领）+ 原有硬件 ID 严格匹配测试。测试 5 / 62 / 53。

### 7.10 更早一次点击暴露的两个缺陷（2026-11-19 18:12 实测）

用户点"一键恢复"后服务端日志：

```
18:12:20 [WRN] VirtualDisplayEnabled 失败 | …（提交变更参数失败：参数错误。）
18:12:24 [INF] 环境状态：PartialFailure | SunshineConfigured=Ok | SunshineRunning=Ok
             | PhysicalDisplayRestored=Ok | VirtualDisplayEnabled=Failed
```

前三步都对（还原配置→重启服务→客户端夺回物理主显成功），只有禁用虚拟设备失败。

1. **DIF 码凭记忆写错**。`SetupDiSetClassInstallParams` 回 `ERROR_INVALID_PARAMETER`：我写的 `DIF_PROPERTYCHANGE=0x0B`、`DIF_REGISTERDEVICE=0x05`，而本机 Windows SDK（`10.0.26100\um\SetupAPI.h`）实际是 **`0x12` 与 `0x19`**；`DICS_ENABLE=1 / DICS_DISABLE=2 / DICS_FLAG_GLOBAL=1 / DIGCF_PRESENT=0x02 / SPDRP_DEVICEDESC=0 / SPDRP_HARDWAREID=1` 猜对。问题码同样按 SDK 核对：`CM_PROB_DISABLED=0x16`、`CM_PROB_DISABLED_SERVICE=0x20`（新增计入禁用判定）、`CM_PROB_FAILED_INSTALL=0x1C`。
   防复发：`VirtualDisplayDevice.TryValidateEnableParams()` 只调 `SetupDiSetClassInstallParams`（不执行变更、不需要管理员），配成普通测试 `EnableParamsStructure_IsAcceptedBySetupApi`——结构或 DIF 码写错会立刻红。
2. **"接管前备份"可能根本不是接管前状态**。`sunshine.conf.guardian-orig` 是在**已经接管**的文件上拍的快照（内容里就带着 `ensure_only_display` 三个键，`File.Copy` 保留源时间戳所以看上去是 11-14 的旧文件）。按它还原会把接管形态再写回去——"一键恢复"变成没恢复。
