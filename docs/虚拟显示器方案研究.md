# 虚拟显示器方案接入可行性研究（Sunshine + Moonlight 熄屏串流场景）

> 研究目标：在 Project Guardian 场景下，验证"虚拟显示器（Indirect Display Driver，IDD）"方案能否实现
> **串流期间物理显示器熄灭，且串流画面稳定流畅**，并给出可落地的集成设计与验证步骤。
> 研究日期：2026-11-14。证据等级标注遵循来源分级（P0 官方/一手、P1 权威二手、P2 专业社区、P3 一般参考）。

## 摘要

- 结论：**方案可行**。虚拟显示器（VDD）是 Sunshine/Moonlight 社区公认的熄屏串流标准解法，Sunshine 官方配置项原生支持"串流时仅激活虚拟显示器、停用物理显示器"（`dd_configuration_option = ensure_only_display`）[cite:1][cite:2]。
- 原理：Sunshine 在 Windows 上基于 Desktop Duplication API 捕获"被流式输出的那个显示器"的 GPU 输出[cite:3]。把流式输出指向虚拟显示器后，物理显示器被停用（无信号、屏幕黑）不再影响捕获管线——捕获与物理显示彻底解耦，规避了当前 `SC_MONITORPOWER` 关屏导致 GPU 输出复位、串流卡顿/无法建连的问题。
- 首选方案：**VirtualDrivers/Virtual-Display-Driver（VDD HDR 版）**。MIT 许可[cite:4]、winget 分发、IddCx 1.10、支持 HDR/自定义 EDID/浮点刷新率[cite:5]；项目自述为**已签名**、以用户态（UMDF/Session 0）运行，不属于典型内核显示驱动[cite:5]（签名状态需在本机安装时实测确认，见第 6 节）。
- Guardian 集成方式：Phase 2 新增"串流隐私（虚拟显示器）"能力——检测 VDD 与 Sunshine 配置状态 → 引导安装/配置（含备份回滚）→ 串流期间显示隐私职责移交 Sunshine，Guardian 的压黑逻辑保持静默 → fail-open 时恢复显示拓扑。
- 主要风险：GPU/芯片组驱动大版本更新与 VDD 冲突可能致开机黑屏（有文档化恢复手段）[cite:5]；Sunshine 异常退出可能残留"物理显示被停用"的拓扑状态，需 Guardian 提供拓扑恢复兜底。

## 1. 背景与目标

Guardian 当前在无 DDC/CI 的机器上以 `SC_MONITORPOWER` 广播实现显示隐私，实测与 Sunshine 帧捕获冲突：周期压黑导致光标卡顿/瞬移、串流无法建立或重连失败（见 `docs/技术兼容性报告.md` 1.1 节）。本研究的假设是：**把流式输出从物理显示器迁移到虚拟显示器，使"物理屏熄灭"与"串流捕获"相互独立**。

目标拆解：

1. 串流期间物理显示器无画面（隐私目标不变）；
2. 串流画面稳定、可建立、可重连（可用性目标）；
3. 不违反 Guardian 安全约束：不引入未签名内核驱动、fail-open 可恢复、界面状态与实际一致。

## 2. 原理说明

Windows 的 Desktop Duplication API 按"显示器"捕获 GPU 输出；显示器被停用（display deactivation）时，其捕获句柄失效，这就是 `SC_MONITORPOWER` 方案在部分硬件上破坏串流的根因。虚拟显示器是 IddCx（Indirect Display Driver，Windows 10 1607+ 引入）框架下的**用户态显示驱动**，向系统呈现一个"虚拟监视器"，GPU 照常向其输出画面[cite:5]。

关键链路（VDD + Sunshine 方案）：

1. 安装 VDD 后，系统多出一个虚拟显示器（如 "VDD By MTT"），可保持"已断开"状态不影响日常桌面布局[cite:6]；
2. Sunshine 配置 `output_name` 指向该虚拟显示器的 `device_id`，并设置 `dd_configuration_option = ensure_only_display`[cite:1]；
3. 串流开始：Sunshine 激活虚拟显示器、停用全部物理显示器 → 物理屏无信号（黑屏），捕获目标为虚拟显示器，全程稳定；
4. 串流结束：Sunshine（libdisplaydevice）恢复串流前的显示拓扑[cite:1][cite:2]。

该链路与 Guardian 现有"串流检测 + 暂停压黑"策略天然兼容：串流期间 Guardian 无需做任何显示操作，仅需如实呈现状态。

## 3. 候选方案对比

| 方案 | 签名/测试模式 | 许可证 | HDR | IddCx | 维护状态 | 与 Sunshine 集成方式 | 主要限制 |
|---|---|---|---|---|---|---|---|
| Virtual-Display-Driver（VDD HDR，VirtualDrivers） | 项目自述已签名[cite:5]（需实测确认） | MIT[cite:4] | 是（10/12bit）[cite:5] | 1.10 | 活跃，winget 分发[cite:5] | output_name + ensure_only_display | GPU 驱动更新冲突风险[cite:5] |
| Apollo（Sunshine 分支，内置 SudoVDA） | 自带驱动，安装流程内置 | GPL-3.0（分支） | 是，按客户端自动匹配分辨率[cite:7] | 内置 | 活跃[cite:7] | 直接替换 Sunshine | 更换整个串流宿主，生态为分支，Windows-only |
| parsec-vdd（nomi-san） | 复用 Parsec 签名驱动 | 仓库 MIT（驱动二进制来自 Parsec，再分发需另核条款）[cite:8] | 否[cite:8] | 1.5 | 慢节奏维护[cite:8] | 需常驻进程每约 1 秒 ping 保活[cite:8] | 无 HDR；显示生命周期绑定控制进程 |
| IddSampleDriver（微软示例） | 未签名（需测试模式/自签证书）[cite:9] | MIT | 否 | 旧 | 示例代码 | 手工安装 | 违反 Guardian 不引入未签名驱动约束 |
| usbmmidd_v2（Amyuni 商业） | 已签名 | 商业许可 | 仅 8bit | 旧 | 商业支持 | output_name | 收费；功能较旧 |
| 硬件假负载（HDMI/DP dummy plug） | 不涉及 | — | 视假负载 EDID | — | — | 输出指向假负载端口 | 需空闲视频输出口；笔记本/核显通常不适用 |

对比结论：满足"已签名 + 免测试模式 + HDR + 活跃维护 + 可再分发"的软件方案中，**VDD（VirtualDrivers）综合最优**；若用户可接受更换串流宿主，Apollo 集成度最高（一步到位）。parsec-vdd 的 ping 保活模型反而适合 Guardian 深度接管（显示随 Guardian 生命周期存在/消失），但缺 HDR 且驱动二进制再分发条款需单独确认[cite:8]。

## 4. Sunshine 端配置要点（官方支持，可复用）

以下均来自 Sunshine 官方文档与配置参考[cite:1][cite:2]：

- `output_name`（Windows）：填写虚拟显示器的 `device_id`（形如 `{64243705-...}`）。官方文档明确 Windows 下以启动日志 "Currently available display devices" 中列出的 `device_id` 为准[cite:1]；社区实践亦确认用 `device_id` 而非 `\\.\DISPLAYn`（后者在新版本逻辑下无效）[cite:6]。
- `dd_configuration_option`：枚举为 `disabled / verify_only / ensure_active / ensure_primary / ensure_only_display`，其中 **`ensure_only_display` 即"停用其他显示器并仅激活指定显示"**[cite:2]。
- `dd_resolution_option` / `dd_manual_resolution` / `dd_refresh_rate_option` / `dd_manual_refresh_rate` / `dd_hdr_option`：控制虚拟显示器分辨率、刷新率与 HDR 行为，可按需跟随客户端[cite:1]。
- 排障工具：Sunshine 自带 `dxgi-info` 工具列出全部输出设备；日志级别需设为"信息"才能在 Troubleshooting 页看到 "Currently available display devices"[cite:6]。

## 5. Guardian 集成设计（Phase 2 建议）

### 5.1 能力检测与状态呈现

- 扩展 `CapabilityReport`：新增 `VirtualDisplayDriverInstalled`、`SunshineVirtualDisplayConfigured`（读取 Sunshine 配置文件 `output_name`/`dd_configuration_option` 与设备列表交叉核对）；
- 主界面新增磁贴或设置项："串流隐私（虚拟显示器）"，状态枚举：未安装 / 已安装未配置 / 生效中 / 冲突；
- 显示隐私磁贴逻辑不变：串流期间如实显示"暂缓/由串流宿主接管"。

### 5.2 引导式安装与配置（含回滚）

- 安装：优先 `winget install --id=VirtualDrivers.Virtual-Display-Driver -e`（需要用户确认 UAC）[cite:5]；失败则引导手工安装（Wiki 流程）[cite:10]；
- 配置 Sunshine：备份 `sunshine.conf` 后写入 `output_name` 与 `dd_configuration_option = ensure_only_display`（仅当用户确认）；修改前校验 Sunshine 服务状态，修改后重启 Sunshine 并验证虚拟显示器出现在设备列表；
- 回滚：保留配置备份与"一键还原"，卸载 VDD 走标准卸载（控制面板或 Device Manager）[cite:10]。

### 5.3 显示隐私职责移交与防冲突

- 当检测到"Sunshine 已配置 ensure_only_display 且虚拟显示器激活"时，Guardian 客户端的压黑执行器保持静默（现有串流检测已覆盖"检测到串流即暂停压黑"，无需改动核心逻辑）；
- Guardian 非串流期间的显示隐私（本地直用场景）继续使用现有 SC_MONITORPOWER/DDC 路径，两条链路互斥由"串流状态"仲裁。

### 5.4 Fail-open 与拓扑恢复

- 风险场景：Sunshine 崩溃/被杀导致"物理显示器仍处于停用状态"的残留拓扑。恢复路径：
  1. 用户按紧急热键（Ctrl+Alt+Shift+F12）→ Guardian 调用 `SetDisplayConfig`/`ChangeDisplaySettingsEx` 重新启用全部物理显示器；
  2. 无 Guardian 时兜底：Win+P 循环切换投影模式（Windows 原生恢复手段，社区验证有效）[cite:5]；
- Guardian 服务端心跳恢复逻辑不变（客户端失联 → 自动恢复），但需新增"显示拓扑恢复"动作项。

## 6. 风险与已知限制

1. **签名状态需实测**：VDD 项目自述"已签名"（对比表）[cite:5]，但历史版本（MikeTheTech itch.io 时代）曾要求安装自签证书/测试模式[cite:11]；本机安装时必须验证：设备管理器驱动签名状态正常、`bcdedit` 未开启 testsigning。若实为自签，则需评估与 Guardian"不引入未签名驱动"约束的冲突，转投 Apollo 或硬件假负载。
2. **GPU/芯片组驱动更新冲突**：官方明确警告大版本驱动更新前应先卸载 VDD，否则可能开机黑屏（Safe Mode 卸载或 Win+P 恢复）[cite:5]。Guardian 可在检测到大版本驱动更新时主动提示。
3. **Sunshine 异常退出拓扑残留**：见 5.4，需 Guardian 提供恢复动作（Phase 2 待验证项）。
4. **多 GPU/笔记本**：Desktop Duplication 只能捕获"用于显示输出的 GPU"[cite:3]；核显+独显混合输出场景需确认虚拟显示器挂在目标 GPU 上（VDD 提供 PCI-bus/LUID 选择能力[cite:5]）。
5. **ARM64**：Windows 11 24H2+ 上可能需要测试模式[cite:5]（本机若为 x64 则不适用）。
6. **Sunshine 配置变更的耦合**：Sunshine 升级可能改变配置项语义（如 output_name 从 display_name 改为 device_id 的社区报告[cite:6]），Guardian 配置写入需做版本兼容校验。

## 7. 本机验证步骤（待执行，需用户确认）

1. 记录基线：当前显示拓扑、Sunshine 版本与 `sunshine.conf` 关键项（备份）；
2. 安装 VDD（winget），验证：设备管理器签名状态正常、testsigning 未开启、虚拟显示器出现；
3. Sunshine 配置 `output_name`（device_id）与 `dd_configuration_option = ensure_only_display`，重启 Sunshine；
4. 验证矩阵：
   - 串流启动 → 物理屏熄灭、Moonlight 画面正常、光标流畅（对比当前卡顿基线）；
   - 串流中反复断开/重连 3 次 → 均成功；
   - 串流结束 → 物理屏恢复、分辨率/刷新率/HDR 与基线一致；
   - 保护开启（Guardian 显示隐私）后再串流 → 无冲突（Guardian 静默、Sunshine 接管）；
   - 紧急热键恢复 + 强制结束 Sunshine 后 Win+P 恢复拓扑；
5. 全部通过后，将结论回填 `docs/技术兼容性报告.md` 显示隐私章节，并把"串流隐私（虚拟显示器）"标记为已验证能力。

## 8. 结论与建议

- **可行性：高**。VDD + Sunshine `ensure_only_display` 是官方支持、社区广泛验证的成熟组合[cite:1][cite:2][cite:6]，原理上彻底消除 Guardian 当前遇到的"关屏 vs 串流"冲突。
- **建议**：按第 7 节步骤在本机执行验证（需用户确认安装内核级显示驱动与修改 Sunshine 配置）；验证通过后在 Phase 2 实现 5.x 的集成设计；验证失败则退路为 Apollo 整体替换或硬件假负载。
- **Guardian 现网行为**：在完成验证前，维持当前"串流期间暂停压黑"的降级策略不变（可用性优先，状态如实呈现）。
